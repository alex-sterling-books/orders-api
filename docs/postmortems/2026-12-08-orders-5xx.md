# Postmortem: Order submissions failed after the v1.9.0 release

**Date:** 2026-12-08 | **Impact window:** 14:09 to 14:45 UTC (36 minutes) | **Severity:** SEV2
**Authors:** On-call engineer, Priya (Orders owner) | **Reviewed by:** Dana (incident commander) | **Status:** Final

> Fictional example for the book *Practical AWS DevOps Agent*. Northwind Supply, its people, and these numbers are invented for teaching.

## Summary

Release v1.9.0 made `orders-submit` reserve inventory before saving each order, and in the same change lowered the function timeout from 10 seconds to 3. About 8 percent of inventory calls take about 3.5 seconds, so those orders timed out and customers saw an error. A promotion burst at 14:20 added DynamoDB throttling, which made the error rate worse for six minutes and led the first diagnosis in the wrong direction. Rolling back to v1.8.0 at 14:44 ended the impact.

## Impact

- About 8 percent of order submissions failed from 14:09 to 14:19 and from 14:27 to 14:44, rising to about 12 percent during the 14:20 to 14:26 burst.
- About 1,200 failed order submissions in total, summed from the per-minute API Gateway 5xx counts.
- No data loss. Orders that succeeded were stored correctly. No partial orders were written.

## Root cause

v1.9.0 added a synchronous call from `orders-submit` to `inventory-reserve` and lowered the function timeout to 3 seconds. Nothing in the release process compared the function timeout with the latency of the calls it waits on. The inventory service's slow path, about 3.5 seconds, was known to the Inventory team but not recorded anywhere the Orders team or the pipeline could check.

## Contributing factors

- **DynamoDB throttling during the promotion burst.** The `orders` table's write capacity was below peak demand. SDK retries added latency and pushed extra requests past the timeout between 14:20 and 14:26.
- **A runbook and skill without timing checks.** Version 1 did not ask whether each signal started before the errors, or whether errors continued after a suspected cause ended. The first diagnosis followed the most dramatic minutes.
- **An alarm that reported symptoms only.** `OrdersApi-5xx-High` showed that orders failed, not that the function was hitting its timeout.

## Five whys

1. Why did orders fail? Because `orders-submit` timed out before it could save them.
2. Why did it time out? Because it waited on `inventory-reserve`, which sometimes takes longer than the new 3-second limit.
3. Why was the limit shorter than the dependency's slow path? Because the timeout was lowered in the same change that added the dependency, and the dependency's latency was not known to the reviewers.
4. Why was it not known? Because no one had recorded a latency budget for the function and its dependencies.
5. Why did nothing catch the mismatch before release? Because the release process checked code correctness and template syntax, but had no check that a function's timeout covers the calls it makes.

## What went well

- The webhook started the investigation four minutes before a person acknowledged the page.
- The on-call engineer's first update stated impact, known facts, and unchecked leads, and named no cause.
- The team tested the agent's hypothesis before acting on it. Raising write capacity, the proposed fix, would not have stopped the failures.
- The rollback had a named approver, written criteria, and a disabled pipeline, and was itself reversible.

## What went poorly

- Nine minutes passed between the alarm and the acknowledgment.
- The first hypothesis came from the loudest six minutes of data, and stood for 12 minutes before it was tested.
- The pull request description mentioned the timeout change, but no reviewer had a way to judge whether 3 seconds was safe.

## Lessons

- A function's timeout is a contract with every service it waits on. Write the budget down, and check it in the pipeline.
- A coherent explanation built from true observations can still be wrong. Compare start times, and check what happens when the suspected cause goes away.
- The agent shortened the investigation and reached the right answer when asked the right question. The verification and the decision stayed with people, which is where they belong.
